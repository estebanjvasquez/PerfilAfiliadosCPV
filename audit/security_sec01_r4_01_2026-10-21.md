## A. CAUSE (installed Shield 3.9.10; vendor not edited)

**What the editor renders.** Every option comes from the server-side schema:
- `RoleResource::form()` → `getShieldFormComponents()`: one `CheckboxList` per registered resource. Its options are `Utils::getResourcePermissionPrefixes($fqcn)` × the resource identifier.
- The pages and widgets lists, minus the configured exclusions.
- The custom-permission list, **only** when `entities.custom_permissions` is on. It is off here.

**What a save does.** `EditRole::mutateFormDataBeforeSave` / `CreateRole::mutateFormDataBeforeCreate` collect every form value except name, guard and select-all. Then `afterSave` / `afterCreate`:
- run `Permission::firstOrCreate` for each value, with the *submitted* guard;
- call `syncPermissions()` with exactly that list.

Consequences:
- **Silent loss:** every permission the form does not render is detached. On staging, 116 permissions have no checkbox, and the app's policies reference 73 of them.
  - They are names of resources that are no longer registered or that now have another identifier, `export_*`, `taxonomy_*`, and old pages and widgets.
  - super_admin holds all 116; the affiliate role holds 35 of them.
- **Forged grants:** Filament's `CheckboxList` does not check submitted values against its options, so any submitted name was created and granted. After R4 only a current super admin reaches this path, but it is still an unbounded write.
- **The toggle is not a fix:** turning the custom tab on would render every non-entity permission and would still create forged names.

## B. REPAIR

**Resource:**
- `App\Filament\Resources\Shield\RoleResource` extends Shield's resource. When the panel already has a `RoleResource`, the plugin skips its own (`Utils::isResourcePublished`); that is Shield's supported way to customise it.
- The form, table, slug (`shield/roles`), labels and navigation are inherited. Only the four pages are app classes.
- A test asserts that the panel serves only this resource.

**Write rule** (`App\Support\Security\RolePermissionSync`, called from `EditRole::afterSave` and `CreateRole::afterCreate`):
- `final = (submitted ∩ editable) ∪ (permissions the role holds NOW outside editable)`.
- **Editable set:** computed on the server from the page's *visible* `CheckboxList` components (`getFlatComponents()`). A disabled tab contributes nothing. Submitted data is never used to build it.
- **Fresh state:** the role row is locked (`lockForUpdate`) and its current permissions are re-read inside the transaction. A stale browser page therefore neither drops a hidden permission added since it was opened nor restores one removed since.
- **Creation:** only an editable name can be created, and always under the role's *persisted* guard.
- **Refused input:** unknown names, numeric ids, hidden names sent through a visible field, and invented form keys are neither created nor granted. Form keys outside the schema never reach the hook.

**Atomicity** (`WritesRenderedPermissionsOnly`):
- Transactions are enabled for the role pages only (the panel default stays off in Filament 3.3.55).
- They run on the role-model and permission-model connections. Spatie writes `role_has_permissions` through the role.
- Filament begins before validation and rolls back on any Throwable. The role row and every link commit together or not at all.
- Spatie's `syncPermissions` detach-and-attach happens only inside that transaction.
- The permission cache is forgotten again after the commit or rollback. Spatie forgets it inside the transaction, where another request could rebuild it from the old rows.

**Unchanged:**
- `RolePolicy`: every request requires a current super_admin and the explicit permission. Filament re-runs `authorizeAccess()` at save.
- `PrivilegedRoleDefinitionGuard`, the R2 account-grant guard and role memberships.

## C. TESTS

`tests/Feature/Security/RoleEditorPermissionPreservationTest.php` has 7 tests. They use literal expectations and the disposable PostgreSQL; synthetic hidden permissions (`zzz_r401_hidden_*`) are permissions with no checkbox. Each test asserts exact permission sets, the `Permission` row count and the role memberships before teardown.

| Test | What it asserts |
|---|---|
| Panel registration | Only the app resource is registered, at the same slug |
| No-change save | Ordinary and privileged roles keep every permission |
| Visible remove and add | One visible checkbox is removed, then an allowed one added; the hidden ones stay. A visible removal on the privileged role keeps its hidden and role-administration permissions |
| Fresh preserved part | Between opening and saving, another writer adds one hidden permission and removes another. The save keeps the new one and does not restore the removed one |
| Forged input | A forged name, an existing hidden permission's numeric id, an unknown id, a hidden name in a visible field and an invented form key, on edit and on create: nothing is created or granted |
| Revocation | A page opened as super_admin saves nothing after the role is removed |
| Injected failure | After Spatie detaches and attaches (`PermissionAttached`), on edit (with a rename) and on create: the role row, every link and the "no role created" state are rolled back |

`RoleAdministrationTest` (R4 denials and the allowed admin path) and `PriorityGlobalSearchTest` now target the app resource. Their expectations are unchanged.

## D. LIVE RESTORATION — PROPOSAL ONLY (nothing restored)

**Source:**
- the restricted read-only baseline from 2026-10-20 and the after-state from 2026-10-21 ~15:20Z, on runtime `cf01e9c`;
- the exact delta, with each name classified, kept in restricted notes;
- the reference check: a literal-name search of the deployed tree (`cf01e9c`: app, routes, config, resources, database, bootstrap).

**Attribution corrected:** the defect removed **109 hidden permissions, all on the role with no users**. The occupied role held no hidden permissions and lost none to the defect. The other non-Role removals were **visible** checkboxes cleared in those saves. `6319591825` had reported "115 hidden plus 1 hidden"; that is superseded.

| Role | Lost | Class | Count | Proposal |
|---|---|---|---|---|
| Occupied (1 user) | 7 | role administration (visible) | 6 | **never** (owner rule) |
| | | user list, read-only (visible) | 1 | restore **only if** the owner confirms its removal was unintended. Implication: it shows the account list (data exposure, not a grant path) |
| Unoccupied (0 users) | 121 | role administration (6 visible + 1 hidden `export_role`) | 7 | **never** |
| | | user management, read (visible) | 1 | not now |
| | | user management, write (visible) | 5 | only on explicit intent. **Escalation flag:** it can assign non-privileged roles to accounts |
| | | hidden, **active** (company-module CRUD; geographic and infrastructure catalog CRUD) | 66 | not now. If the role is used again, decide as a set. Catalog writes are the F-03 risk class |
| | | hidden, **unreferenced/legacy** (`export_*`, old pages and widgets) | 42 | do not restore |

**Least-change recommendation:** restore **at most 1 link** (the user list on the occupied role, if confirmed) and **0** on the unoccupied role.

**Preconditions for any restoration:**
- owner approval;
- **after** this fix is deployed, otherwise the next save through the editor drops them again;
- a reviewed transactional script, never the editor;
- a permission-cache reset and a read-only re-verification.

## REMAINING_RISKS / LIMITATIONS

- **Until this candidate is deployed, saving any role in the live editor drops its hidden permissions.** Do not save roles there, especially super_admin (116 hidden) or the affiliate role (35 hidden, 323 accounts).
- A stale page still has last-write-wins on its **visible** checkboxes; that is the normal semantics of editing. The hidden part is always read fresh.
- Changing an ordinary role's guard while it keeps permissions under the old guard is refused by Spatie, and the whole save rolls back.
- No browser run. The behaviour is server-side and covered by Livewire tests.
- R3-02, R3-03, F-03, F-06, 14 relation managers, 9 search resources and SEC-02 to SEC-05 are unchanged and open. SEC-01 stays open.
